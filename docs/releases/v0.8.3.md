# v0.8.3

A quota slack shipped in 0.8.2 could be wrong, and wrong in the direction that matters: it read a
counter that had already been reset.

A `used_percent` is only true while the window that counted it is still running. Past its
`resets_at` the counter has emptied and the stored number describes a past that no longer applies.
Reading an 11-hour-old capture and announcing "17% slack" when the 5-hour window had turned over
since is stating something false with the face of a fact. The next capture put the same account at
77%.

The windows are independent — 5 hours and 7 days tighten separately — so the rule is per window:
drop the ones that have reset, and take the slack from the tightest of those still running. Against
the reading that produced the bug, the corrected rule yields 77%, matching the capture that came
later.

When **every** window has reset, slack is now `null` — unknown — rather than 100%. An emptied
counter is the strongest hint of a free account there is, but "probably free" is not "free", and
returning 100% put a worker nobody knows anything about ahead of one with measured room.

For the same reason `--worker auto` now treats unknown slack as worse than any measured slack. With
nothing known on either side it still falls back to the least-load rule, exactly as before quota
existed, so a machine with no quota cache behaves as it always did.

## Verification

`npm test`: 36 suites, 307 tests, 307 pass, 0 fail (three consecutive clean runs). Four new tests
cover the rule, using the real numbers that exposed the defect.
