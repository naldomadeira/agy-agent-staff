# v0.7.9

## `--worker` is refused where it does nothing

`--worker` lived in the global flag set, so every subcommand accepted it and most of them
ignored it without a word:

```
$ agy-companion.mjs status --worker bogus
No agy-staff jobs recorded in this repository.
$ echo $?
0
```

Anyone writing `wait <id> --worker agy2` to pin a worker came away believing they had done
something. The same file already takes the opposite line elsewhere — `loadProjectConfig` dies on
a corrupt config with the reason written out, that a policy silently ignored is worse than an
error. This applies the same rule to the flag.

`status`, `wait`, `result`, `cancel`, `observe`, `setup` and `workers` now refuse it:

```
agy-staff error: --worker has no effect on status: it only selects a pool worker when starting
or resuming a run (staffer, research, review, implement, ask, continue, restart)
```

Exit code 1, the same as every other argument error.

`workers` is in that list on purpose. It lists the pool, so `--worker <id>` there would mean
filtering the listing — a new feature, not a fix, and out of scope.

The subcommands that do use it are untouched: the run modes reach it through `planWorker`, and
`continue`/`restart` keep their affinity logic unchanged. Without `--worker`, nothing anywhere
behaves differently.

## Validation

- `npm test`: 228 passing, 0 failing, 31 suites (219/30 before, plus 9 new).
- The seven refusal cases were run against the previous `companion/agy-companion.mjs` and fail
  there — the flag is accepted and ignored, exactly as reported.
- `npm run check:pi`: 13 files, 0 changed.

`docs/REFERENCE.md` described `--worker` as "ignored by modes that never reach agy", which is no
longer true; both it and the Chinese mirror now say where the flag is valid and where it is
refused.
