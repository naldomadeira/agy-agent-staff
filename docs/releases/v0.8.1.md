# v0.8.1

## `wait --follow` shows what the job is doing

An agent dispatches a job and runs `wait <id> --timeout 10m` in a background shell. That shell
then prints nothing for minutes — in Claude Code the shell panel reads `No output available`
while agy works. One job ran for 4m33s, wrote no files, and nobody saw, because there was
nothing to see.

The silence is deliberate, and stays the default: `cmdWait` says so in a comment, and the jobs
skill calls a pending wait "necessary result collection, not active observation". What was
missing was the option to look.

`--follow` streams the job's steps to **stderr** while wait polls, and leaves stdout exactly as
it was — the result, delivered verbatim, which is what callers parse.

```
$ wait research-mu7mw7o3 --follow --timeout 10m
  41 ▶ run_command pnpm typecheck
  41 ✓ run_command pnpm typecheck (5.5s)
  42 ▶ view_file index.d.mts
# Job research-mu7mw7o3 (research, done) — AGY worker: agy2 (agy2; 1.2.6)
```

`▶` is a step starting, `✓` one that finished with its duration, `✗` an error.

It reuses the existing 200ms poll loop rather than adding a timer, and reads only the bytes
appended to `jobs/<id>.events.jsonl` since the last tick, keeping a partial trailing line in a
buffer — the worker may be mid-write. A missing or unreadable events file degrades to a no-op:
the result is never put at risk by the progress display.

Steps with no tool — the model's own prose — are not shown. One `agent_response` per tool call
would bury what the job is actually doing under what it is thinking.

Nothing is replayed. The follower starts from the file's current size, so a job that was already
finished when `wait --follow` was called prints nothing and is collected as always. That is not
only a choice: a job that ends `done` with no warnings unlinks its own events file, so there
would often be nothing left to replay.

`--follow` is valid on `wait` alone and refused elsewhere, consistent with the flag scoping added
in 0.8.0.
